# NovaWatch

A mobile-first PWA for tracking TV shows and movies — search, add to a library, mark episodes/movies watched, log rewatches, and get release alerts. Built on Firebase (Auth + Firestore) and the TMDB API, with JustWatch-sourced "where to watch" availability.

Live at `https://www.novawatch.site/`. Mobile-first by design — phones get the primary, fully-tuned experience; tablets get a widened version of the same layout (see Tablet/larger screens below) rather than a separate design. No desktop/laptop-width layout is planned.

## File structure

```
├── index.html              The app itself — auth, Home/Search/Library/Upcoming

│                            above, once OneSignal is configured (see Notifications
│                            below) — inert, harmless to deploy even before then
├── styles/
│   ├── tokens.css          Shared design tokens (colors, light/dark palette) — the one
│   │                       source both HTML pages link, so they can't drift apart
│   └── app.css             index.html's component styles
├── scripts/
│   └── app.js              index.html's application logic (~7,600 lines, classic script —
│                            not type="module", since the markup calls global functions
│                            directly via inline onclick="...")
├── privacy-terms/
│   └── index.html          Privacy Notice & Terms of Service, opened in-app as a full-
│                            screen overlay (openPageOverlay('privacy-terms/'))
├── send-release-notifications.js  Server-side scheduled job — not loaded by the app
│                            itself — that decides what to notify about and sends via
│                            OneSignal. See PUSH_NOTIFICATIONS_SETUP.md.
└── .github/workflows/release-notifications.yml  Optional free daily schedule for the
                             script above, via GitHub Actions
```

`privacy-terms/index.html` deploys one folder level deeper than `index.html` (i.e. `novawatch.site/privacy-terms/`) and links `styles/tokens.css` as `../styles/tokens.css` to account for that. It also keeps its own copies of a handful of `app.css` component classes (`.analytics-card`, `.section-title`, `.section-header`) so it matches the rest of the app's visual language without linking the full stylesheet, whose global `body`/`h1`/`a` rules are tuned for the app shell specifically.

## Tech stack

- **Firebase Auth** — email/password and Google sign-in
- **Firestore** — the only backend; no server of NovaWatch's own
- **TMDB API** — search, metadata, episode/season data, recommendations
- **JustWatch (via TMDB)** — streaming availability by region
- **TVmaze API** — real per-episode broadcast/cable airtimes, used for TV episode release timing (see the TV episode release timing feature entry below). No API key required. Not used for streaming shows - see that entry for why.

### Firebase plan

Currently on the free **Spark** plan. This is a real constraint on the feature set: Spark doesn't include Cloud Storage, which is why avatars are a curated set of 8 hosted images rather than user uploads. Anything that needs Storage stays deferred until there's a reason to move to the paid Blaze plan.

### Data model

- `users/{uid}` — profile doc: `profiles` (array, currently always a single entry), `activeProfileId`, `region`, `username`
- `users/{uid}/library/{itemId}` — each tracked movie/TV show
- `users/{uid}/archivedShows/{slug}` — shows removed from the library but kept for history purposes
- `usernames/{lowercased-username}` — `{uid, username}` reservation docs, used to enforce unique usernames (see below)

**Security rules** live in their own document, `firestore-rules.md`, kept up to date separately from this file — check there for the current recommended ruleset and whether it's actually been applied in the Firebase console yet.

## Core features

**Library & search** — TMDB-backed search; add movies/TV shows; mark watched with a single tap (no rating/reaction popup in the way).

## Library

Redesigned as a central content-management home rather than a straight-to-search-results view - the Library tab itself now shows three things, in order: a horizontally-scrolling **Lists** row, a **TV Shows** preview (up to 9 titles), and a **Movies** preview (up to 9 titles), each with its own "View All". All three sections share `.tab-content-wrapper`'s own consistent spacing, the same pattern Home uses, rather than each section supplying its own inconsistent margin.

**Lists** — the first list card is always the automatic **Favourites** list, which isn't a real document at all (`getFavoriteListItems()`) - it's every library item with `isFavorite` set, computed fresh every time rather than a separately-tracked collection, so favoriting something (the heart icon in the Details modal's header) never needs a second write to keep a list in sync with it. Everything after Favourites is a real user-created list (`users/{uid}/lists/{listId}`, `{ name, itemIds, createdAt, backdropUrl }`) - shows and movies are treated identically, so a single mixed list is completely normal. Each card shows a single full-size backdrop image - a deliberately-chosen one if set (see Custom list backdrops below), otherwise auto-picked from the first item in the list that actually has one - with a name/count label over a flat dark scrim. This replaced an earlier 2×2 poster collage design: a landscape backdrop already matches this card's own 2:1 aspect ratio the way a portrait poster never did, and the collage broke down visibly for any list under 4 items (the common case, not a rare one) by leaving empty quadrants. Falls back to a plain surface color only if literally nothing in the list has a backdrop. Card width is worked out exactly, not approximated: 3 poster columns plus the 2 gaps between them, in the grid directly below it, mathematically works out to just the grid's own full row width - so the card matches it exactly rather than an eyeballed percentage. Tapping a card opens its detail view; a small corner button on each poster there removes it from just that list (or unfavorites it, for Favourites) without ever touching whether it's still in the library at all - deliberately a separate, simpler card renderer from the shared library grid's own cards, specifically so it can't accidentally trigger the library's own swipe-to-remove-from-library gesture.

**Custom list backdrops** — a list's action row opens a picker showing the backdrop image of every item already in that list - tapping one sets it as the list's own `backdropUrl`, taking priority over the auto-picked backdrop that would otherwise show. There's no image upload or external search involved; a list can only ever use a backdrop from something already in it, since a personal list has no TMDB entry of its own to pull alternate images from. Available for the automatic Favourites list too now (unlike Rename/Delete/Share, which still don't apply there) - since Favourites has no list document to store a `backdropUrl` on, its choice saves as `favoritesBackdropUrl` on the account's own document instead, which the existing boot-time profile load already spreads into `state` with no separate fetch needed to read it back.

**Auto-picked backdrops reflect real recency** — when no custom backdrop is set, the card shows whichever item was added or favorited most recently that actually has a backdrop image, not just the first one found. Favoriting something new updates the card immediately; un-favoriting it correctly falls back to whichever favorite is now the most recent, not an arbitrary one. This needed a real fix, not just a different sort: `getFavoriteListItems()` previously returned favorites in whatever order they happened to sit in `state.library`, with no sense of "recent" at all - favoriting now records `favoritedAt`, and that list sorts by it. Regular lists work the other direction: `itemIds` is already chronological (oldest first, since adding appends to the end), so the auto-pick searches that array in reverse instead of adding a second timestamp field for something the existing order already encoded.

**Choosing a backdrop pulls the real TMDB gallery** — not just the single backdrop already saved on each item in the list. Opening the picker fetches every available backdrop for every item in the list in parallel (`fetchItemImages()`, the same per-title alternate-image gallery the individual poster/backdrop picker already used), capped at 8 per item so a larger list doesn't turn into an unmanageably long grid.

**Reordering includes Favourites now, not just custom lists** — the "Reorder" button next to "+ New" treats every entry, including the automatic Favourites list, as part of one unified ordering. Favourites has no list document of its own, so its position saves as `favoritesOrder` on the account document instead - the same pattern `favoritesBackdropUrl` already established - unified into the same sort as real lists (`getOrderedListEntries()`), defaulting to "first" so nothing changes for anyone until they actually move it.

**Every list mutation updates instantly, not on a round-trip** — adding or removing an item, renaming, creating, deleting, reordering, and changing a backdrop all update the local copy of the data immediately, before (or alongside) the actual Firestore write, with the affected view(s) re-rendered right away. This wasn't originally true across the board: several of these had no local update at all and relied entirely on the real-time listener eventually catching up once the write round-tripped back from the server - correct, but not instant, and on a slow connection genuinely noticeable. Reordering specifically had a real bug, not just a missing optimistic update: the swap was mutating a copy of each entry's `order` field rather than the real object in `state.lists`, so a move only ever appeared to take effect once the listener did the work anyway - fixed to mutate the real object directly. Every one of these local updates also rolls itself back on a genuine write failure (not Firestore's own offline retry queue, which resolves on its own) - added an item, saw it appear, then the write actually failed for some other reason - rather than leaving the screen showing something that didn't actually save. Deleting a list follows the same principle at the modal level: closing the list's own detail view used to happen unconditionally, even on a failed delete, which looked like success right as an error toast said otherwise - now it only closes on a real success.

**Long-press a list card to jump straight to its backdrop picker** — the same 600ms long-press gesture (with the same move-cancellation and click-suppression) already used to change an individual show or movie's poster/backdrop, applied to list cards specifically so changing a list's backdrop doesn't require opening its detail view first just to reach the button in there.

**Reorder lists** — a "Reorder" button next to "+ New" opens a plain list of every list (Favourites excluded - it's always pinned first, not something with a position of its own) with move-up/move-down buttons per row, not drag-and-drop. Genuine drag gestures are inconsistent across touch, mouse, and different browsers - native HTML5 drag-and-drop in particular barely works on touch devices at all - where a plain button tap behaves identically everywhere this app runs. Backed by an `order` field on each list document, only actually written the first time anyone reorders anything at all (backfilled onto every list at once, from whatever order they're already showing in, so nothing visibly jumps that first time) - before that, everyone keeps seeing creation order exactly as they always have.

**TV Shows preview** — up to 9 titles, entirely automatic, in priority order: shows genuinely in progress (watched some, not all, released episodes - not Home's broader Continue Watching definition, which also includes shows never started), then shows fully caught up with everything currently out, both tiers sorted by the viewer's own most recent watch activity (a distinct sort from the latest-aired one the full category view below uses, since "when did TMDB say this released" and "when did I actually watch it" are different questions).

**Movies preview** — same shape, adapted for movies not having partial progress: recently-watched movies first, then unwatched-but-released ones filling any remaining slots, so a library with little watch history yet still shows something rather than a sparse preview.

**View All** opens the same segmented TV/Movies view (category blocks - In Progress, Up to Date, Finished, Unwatched, Coming Soon, Stopped Watching) that used to be the whole Library tab directly, relocated into its own modal (`#fullLibraryModal`). The TV/Movies toggle and search bar that used to live inside that modal are gone now - each section's own "View All" already says which one you want before the modal ever opens, so a second way to switch (or search) once inside was redundant. Every category, in both TV and Movies, sorts by release date, latest first, as one single consistent rule - previously movies' Unwatched and Coming Soon categories had no sort at all, and Watched sorted by a different dimension (when you watched it) than every TV category already did (when it aired), which read as arbitrary rather than "latest to oldest" as one coherent idea.

Poster grids across Library and the list detail view use targeted DOM reconciliation (`syncCardGrid`) rather than replacing the whole container on every update - a single card's own content changing (a progress bar updating) used to mean every card in that grid got its `<img>` destroyed and recreated, which is what was actually causing posters to visibly flicker on a library change, a tab switch, or a modal opening, even for cards whose own data never changed. Only the specific cards that actually changed get touched now; everything else keeps its already-decoded image completely untouched. The Full Library modal's category view (In Progress, Finished, ...) now gets the same treatment via `renderCategorizedLibrary` - it checks whether the actual set of categories present genuinely changed (a show moving between categories, one appearing or emptying out) before deciding how to update: same categories in the same order reconciles per-card as above, a real structural change still gets a full rebuild of just that view, since keyed-diffing whole categories appearing and disappearing wasn't worth building for how rarely it happens.

**Share a list** — a list's header has a Share button alongside Rename/Delete/Backdrop (same visibility rule: not shown for the automatic Favourites list). Genuinely different from sharing a show/movie/episode, which just point at public TMDB data with nothing to protect - a list is private data behind Firestore rules, so a friend's account could never read `users/{uid}/lists/{listId}` directly even with the exact path. Sharing instead writes a lightweight, standalone snapshot - just the list's name and a plain `{tmdbId, type, title, poster}` array for whatever was in it at share time - to its own top-level `sharedLists` collection, fully decoupled from the owner's private library/lists structure. That collection needs its own separate security rule: publicly readable by exact document id (`allow get: if true`) so a recipient's account, whatever it is, can open the link, but never listable/enumerable (`allow list: if false`), so nobody can browse other people's shared lists without a direct link to one. A snapshot is immutable once created - if the original list changes later, an already-shared link keeps showing what it looked like at share time. Opening a shared link shows a plain read-only viewer (no rename/delete/remove/backdrop, since the recipient doesn't own it) - tapping an item opens the normal Details preview for it, the same path any other shared show/movie link already uses, so it can be added to the recipient's own library the ordinary way.

**Rewatch tracking** — per-episode for TV, per-title for movies, via a tap-to-manage popup (Add/Remove Rewatch) rather than a one-way counter. Unwatching something clears its rewatch history. A season can also be bulk-rewatched (or have its rewatches cleared) once every released episode in it has been watched at least once — gated behind a long-press on that season's tab, or the "Mark All Episodes Watched" button for the whole show at once.

**Opening a TV show's details** — lands on the season containing the next released-but-unwatched episode (`getCurrentSeasonForShow`) and auto-scrolls the episode list straight to that row, rather than opening at the top of Season 1 and leaving the person to hunt for where they left off. A caught-up show lands on the season of its most recently watched episode instead. A show with nothing released and unwatched yet (nothing to scroll to) simply opens at the top, same as it always did.

**Search → For You** — TMDB `/recommendations` seeded from your library, ranked by cross-seed hit count then TMDB score. Falls back to plain Trending when the library's empty for that content type.

**Continue Watching** (Home) — the next unwatched episode for every in-progress show, plus any unwatched movies. Swipeable: right reveals "mark watched", left reveals "remove" (or "stop watching" for a TV show with progress already logged, which keeps its watch history instead of deleting it). Marking an episode watched this way also shows how many episodes are left in that show, if any.

**TV episode release timing** — every episode carries a real release instant again, timezone-correct for every viewer. This was fully removed at one point (see the git history of this file for that saga) after a long series of attempts kept surfacing new edge cases. Brought back deliberately differently: rather than one formula trying to cover every show, each episode is anchored one of two ways -
- **Broadcast/cable shows** — a real, network-announced local airtime from TVmaze, when TVmaze lists the show under a real `network` (not a `webChannel`). Converted DST-aware via the same `getTimezoneAnchorUTC` helper movies already used, just pointed at the network's own timezone instead of always Pacific.
- **Everything else** (streaming, or no TVmaze match at all) — the same midnight-Pacific streaming convention movies use. Deliberately the *latest* time in the range real streaming platforms actually use (official Netflix/Disney+ policy; most others release earlier in the evening PT), so this can under-promise (show "not released yet" for a few extra hours on an early-release platform) but never over-promise (claim something's out before it verifiably is, anywhere).

Only the calendar DATE this produces is meant to be trusted per viewer timezone - not the exact hour. `isReleased()` does an exact-instant comparison (not a calendar-day one), so a not-yet-released episode can't be marked watched, doesn't count toward Library/Continue Watching progress, and shows a countdown instead of "Unwatched" in the episode list and details modal. TVmaze resolution (`resolveTVmazeShow`) is cached per show on `tvmazeId` so a show only gets searched for once; a show TVmaze doesn't have just stays on the streaming default, same as every show did before this feature existed - never a hard failure. Movies are unaffected — same convention as before.

**Content rating** — PG-13, TV-MA, etc., shown as a badge in the details modal for both movies and TV shows. Fetched from a separate per-region TMDB endpoint (`release_dates` for movies, `content_ratings` for TV), tried in the viewer's own streaming region first, falling back to US.

**Collection/franchise info** — for movies that TMDB has flagged as belonging to a collection (e.g. "Part of The Dark Knight Collection"), shown in the details modal. Movie-only; TV doesn't have an equivalent concept in TMDB.

**Viewing Analytics** (Home) — total watch time (including rewatch passes), with a current-streak badge underneath it (consecutive calendar days with at least one watch/rewatch logged - resets to zero the moment a day is missed, distinct from the all-time-record "longest streak" the streak achievements track - a solid gray pill while live, a lighter, more muted one when there's no active streak), and counts of watched movies/shows/episodes/rewatches in the tile grid below. Sits below Continue Watching, not above it - the thing you actually act on (what to watch next) leads; stats and streaks are motivating, but secondary to that.

**Achievements** — computed client-side from library data on every load, not stored as separate synced records; only the small "which ones are unlocked" array is persisted. Bidirectional — unwatching something can revoke an achievement it had unlocked, not just grant new ones. Four free-tier achievements are currently active (10 movies watched, 10 shows completed, a 7-day watch streak, first rewatch logged); a second, larger premium tier exists in code (`PREMIUM_ACHIEVEMENTS`) but isn't switched on.

**Sharing** — deep links for a show/movie (`?share_type=tv|movie&share_id=<tmdbId>`) or a single episode (`?share_type=episode&share_id=<showTmdbId>&share_ep=<sXeY>`). Opening a shared episode link loads the parent show first, then drills into that specific episode.

**Unique usernames & display names** — every account reserves a unique, lowercase-only username (`[a-z0-9._]`, 3–20 characters), chosen at signup or via a blocking "Choose a username" screen for Google sign-in / any pre-existing account without one. Separate from that is a freely-editable **display name**, shown everywhere in the UI instead of the username — both are visible together in Settings (`Display Name` / `@username`). See `firestore-rules.md` for how username uniqueness is actually enforced.

**Auth flow feedback** — sign-in, sign-up, Google sign-in, password reset, and account deletion all show errors and confirmations inline, in the form itself (a darker, heavier gray for errors, a lighter one for the couple of confirmations with no other visible state change, like a password reset email - the same weight-based distinction the rest of the app's danger/success tokens use now that neither has a color of its own) - not via a toast, since toasts don't exist in this app. This matters more here than almost anywhere else in the app: a validation error with no visible feedback at all (a blank email field, a wrong password) would otherwise leave someone tapping a button that does nothing, with no way to tell why.

**Settings** — reachable via the button on Home's identity card, which becomes a close (X) button while Settings is open. Organized into two sections: **Preferences** (appearance, streaming region, notifications) and **Library** (Library Display, achievements) — plus NovaWrapped, sign-out, account deletion, and Privacy & Terms below those. Structurally matches every other tab (same padding, same section-title sizing, same spacing rhythm) rather than being a visually separate design.

**Streaming region** — a full ISO 3166-1 country picker, still fully manual and editable at any time; auto-detected on first sign-in via the browser's real Geolocation API (reverse-geocoded to a country through a free client-side lookup) when available and granted, falling back to a locale-string guess for every failure mode - no geolocation support, permission denied, a timed-out/failed lookup, or an unsupported country. Drives which "where to watch" info TMDB/JustWatch returns.

**Dark mode** — a three-way Light/Dark/Auto toggle in Settings. Saved to `localStorage` (device-level, not synced across devices) and applied before first paint via an inline script in each page's `<head>`, so there's no light-then-dark flash. Auto follows the OS setting live via a `matchMedia` listener.

**Notifications** — real push, delivered even when the app is fully closed, via OneSignal (`ONESIGNAL_APP_ID` in `scripts/app.js`, inert until that's actually configured - see `PUSH_NOTIFICATIONS_SETUP.md`). The only notification delivery mechanism in the app - a single on/off toggle in Settings ("Stay in the loop"), no per-category selection, and no separate client-side path that fires while the app happens to be open. The client only handles subscribing a device and requesting permission (which OneSignal's own subscription flow needs regardless of who triggers a send) and tying that device to the signed-in account; a separate server-side script (`send-release-notifications.js`, not loaded by the app) does the actual "what to send, to whom, today" decision on a schedule, since a closed browser tab can't run anything itself. Never at the moment TMDB/TVmaze data merely mentions something, and never for episodes that were already out when a show was added, since a freshly-added show's full episode list is already in hand at add time. Every release-day category shares one notification title, "New Release" — the body carries the specifics, a natural clause per item rather than a "Title - Subtitle" template ("Show Name S1E3: Episode Title is out now" for TV, "Movie Name is out now" for movies) - the earlier "Show Name - Season X Episode X release" wording read as a noun phrase bolted onto another noun phrase, not something anyone would actually say, and didn't even name the episode despite that being available data. The "Stay in the loop" button, and every other on/off-style status in the app (Library Display), share one lighter-gray (on/enabled) / darker-gray (off/blocked) visual language - a device that can't support notifications at all shows a neutral muted state instead of the "off" treatment, since that's a device limitation, not something the person chose to turn off.

**Engagement reminders** — a streak reminder and a Continue Watching reminder, each only ever checked on a day when nothing in the library is actually releasing (never alongside a real release notification). The streak reminder fires once, only when a real streak built from watching yesterday hasn't been extended yet today. The Continue Watching reminder now names a specific, randomly-picked item - a TV show's actual next episode (the same "lowest season, then lowest episode number, among released-and-unwatched" rule the app's own Continue Watching row uses, so it always matches what the app itself would show as next), or an unwatched movie - rather than a generic "you have something waiting," and fires only after 3+ days of no watch activity at all, with its own separate 7-day cooldown once sent, so a quiet stretch reads as an occasional nudge rather than a daily one. Both run entirely server-side, sharing the same UTC-based watch-date data movies/episodes already use for the streak achievement and the Home tab's Current Streak badge. Two separate scheduled runs, not one - release notifications and engagement reminders fire at different times of day on purpose, not just because they're logically distinct: keeping real separation between the two means a "watch something today" reminder doesn't compete for attention with the same morning release check, and lands at a point in the day someone's meaningfully more likely to actually be looking at their phone than at 08:00 sharp. Every account is still processed on the same single pass for whichever concern that particular run covers, so the actual local time either kind of notification arrives at still depends on how far an account's timezone sits from whichever UTC anchor that run uses. OneSignal push is the only notification mechanism in the app - no separate in-app log or list of past notifications.

**Library Display** (Settings) — Finished, Unwatched, and Stopped Watching (the three TV Library categories that hide content the person is done with, hasn't started, or chose to stop, one way or another) can each be shown or hidden independently - on (lighter gray) by default, off (darker gray) once the person turns one off. Purely a display filter - hiding a category never touches the underlying watched/stopped data, it just skips rendering that category block.

**Avatars** — 8 curated hosted images, assigned at random to a new account and always changeable via the picker in Settings.

**PWA install shortcuts** — long-pressing the installed app's icon offers Search/Library/Upcoming as direct shortcuts (Home is skipped, since it's already the default landing).

**Upcoming** (4th bottom-nav tab) — every not-yet-released movie and TV episode from the library (every queued-up episode per show, not just the next one). Same structure as Library: a TV Shows/Movies segmented toggle (`setUpcomingView`), the same search box per sub-view (filters by title, same debounce), each sub-view rendered with the exact same category-block/poster-grid card component Library uses (including the same long-press-to-change-poster gesture, since these are already-tracked library items), just bucketed by Today/Tomorrow/This Week/Later instead of watch status. Each card adds one single-line caption under the title (season/episode + countdown, or just the countdown for movies) since an upcoming item needs its release status spelled out in a way an already-added Library item doesn't. Tapping a card opens the usual details modal.

**Bottom navigation** — a floating "Liquid Glass" pill bar, 4 tabs (Home/Search/Library/Upcoming). An edge-to-edge, flush-to-the-bottom version was tried and reverted after not looking right on real devices - back to the original floating pill, with margin on every side. Supports both tapping a tab and dragging a finger across the bar to switch tabs, with the pill indicator tracking the finger continuously during a drag and settling into place on release. The indicator measures whichever button is active at render time, so it isn't hardcoded to any particular tab count.

**Change-aware list rendering** — Library, Continue Watching, and the episode list inside a show's details modal only touch the DOM when their content has genuinely changed, rather than rebuilding on every periodic background sync (or every time the modal refreshes) regardless. Rebuilding unconditionally was destroying and recreating every poster/thumbnail/episode-still image element each time, which read as flashing even though nothing had actually changed.

## NovaWrapped

A Spotify-Wrapped-style yearly recap, gated to release **January 1, 2027** — before that date, tapping its "View" button in Settings shows an error toast explaining when it opens. The `novawatch` account (the developer's own) can preview it early regardless of the date - a plain client-side check against that account's own username, not a Firestore rules change, since it's reading data the signed-in account already legitimately has access to. Lives as a modal (`#novaWrappedModal`), not a separate page, so it shares the same signed-in session's data as the rest of the app instead of loading a second copy of the Firebase SDK.

Picking a year lands on a full-screen, story-style slideshow - tap through (or tap the left/right edge of the screen, the same interaction as Instagram/Snapchat stories), with a progress bar across the top. Each slide gets its own high-contrast flat gray background - distinct from each other through lightness alone, individually checked at 9.5:1 contrast or better against the white text on top - deliberately more dramatic than the rest of the app's subtle glass language, a recap is meant to feel like a celebration, not another settings screen. The sequence: total watch time (the big hero number) → movies → TV episodes/shows → the most-watched show (its real poster blurred into the slide's own background) → busiest month → rewatches → a final recap card summarizing everything at once, with a real Share button. A slide only exists if there's actually something to say for it - a year with no rewatches simply has no rewatch slide, rather than a hollow "0 rewatches."

Navigation got a real pass: visible, tappable arrows now sit alongside the invisible full-bleed tap zones, not instead of them - a full-screen tap-anywhere zone is the established convention for story formats, but it's only discoverable if you already know that convention exists. A visible arrow means someone seeing this for the first time doesn't have to guess where the screen is even tappable. The progress segments across the top are tappable too now, jumping straight to that slide rather than only ever being able to step one at a time. The landing screen's own title picked up the same flat dark color the "View My Wrapped" button already used, tying the two together into one considered identity instead of a plain heading sitting above a bold button with no visual relationship to it.

Tracks January 1 – December 31 UTC, with a 7-day grace period after account creation excluded (so bulk-adding existing watch history right after signing up doesn't count as binge-watching). Rewatches get their own dedicated slide as a fun fact, but are still deliberately **excluded** from the main Total Watch Time hero number, unlike Home's Viewing Analytics, which deliberately *does* count them toward its own total — that inconsistency between the two is intentional, not a bug.

## Achievements

13 free-tier achievements, each computed from `state.library` directly rather than tracked as separate events - `computeAchievementStats()` derives everything (watch counts, streaks, and the newer ones below) fresh from what's actually in the library, so there's nothing to get out of sync with the data itself. Beyond the original four (10 movies, 10 shows completed, a 7-day streak, a first rewatch), nine more avoid just being bigger-number versions of the same four: **Night Owl** (watch something between midnight and 5am), **Time Capsule** (something released 25+ years ago), **Opening Weekend** (watched within 3 days of release), **Marathon Day** (5+ episodes of the same show in one day), **Double Feature** (a movie and an episode on the same day), **The Collector** (100+ library titles), **List Maker** (3+ custom lists), **Heart Eyes** (10+ favorites), and **Word of Mouth** (shared anything at all - a show, movie, episode, or list). That last one is the one genuinely new *kind* of fact being tracked, not just derived from existing library data - `markHasShared()` sets `hasSharedSomething` on the account document the first time any of the three share functions actually succeeds, and stays true permanently once set.

## Design system

`tokens.css` defines the shared "Liquid Glass" visual language — translucent, blurred, low-opacity surfaces with a soft diagonal sheen — used consistently across the whole app (cards, sheets, buttons, the search bars, the bottom nav) rather than each surface inventing its own treatment. A defined corner-radius scale (`--radius-xs` through `--radius-2xl`) assigns a consistent roundness by component role — e.g. every poster thumbnail across every tab uses the same radius, regardless of which screen it appears on.

**Fully monochrome now — no hue anywhere in the app's own UI.** Every color token (the blue accent family, the orange/red/green gradients, success/danger, the page background mesh) is black, white, or a genuinely neutral gray (r=g=b, not a "cool gray" with a hidden blue undertone - an earlier pass through this conversion used Tailwind's own gray scale, which does have that faint lean, and got corrected once that was noticed). Danger and success no longer have any color to signal severity with, so that distinction now lives in weight instead - danger reads as the darkest, heaviest gray in the scale, success the lightest, the same "seriousness" ordering hue used to carry, backed up by the icon and label next to it the way it already was. NovaWrapped's 8 per-slide backgrounds - deliberately vivid and distinct from each other by design - lost their color too, and stay distinct through lightness alone now (each a different flat shade, individually checked at 9.5:1 contrast or better against the white text on top). Two things are deliberately exempt: photographic content (posters, backdrops, avatars) is real photos and illustrations, not part of the app's own palette, the same way converting every movie poster to grayscale was never actually in scope; and the "Sign in with Google" button's logo keeps its official multi-color mark, since Google's own branding guidelines require it be used unaltered, and a recolored version would also read as a plausible spoofed sign-in button rather than the real one.

**No gradients anywhere either, on top of no color** — every button fill, card background, NovaWrapped slide, and highlight effect that used a gradient is a flat value now. The four color-family tokens (`--blue-gradient`, `--orange/red/green-gradient`) were renamed too, not just re-valued - `--accent-fill`, `--warning/danger/success-fill` - since keeping a name like `--blue-gradient` around for something that's neither blue nor a gradient anymore would have been actively misleading to work with. Two effects that were gradients *by definition* couldn't just be flattened: the skeleton loaders' shimmer became a plain opacity pulse instead (still signals "loading," just via fading rather than a moving highlight), and the bottom nav's own decorative shimmer sweep was removed outright, since unlike the skeleton's it signaled nothing - it was purely a shine effect with no substitute worth forcing in its place. A few legibility scrims (text over a photo needing extra contrast) were genuinely functional gradients, not decorative ones - fading darker specifically where text sits. The list card's scrim got a better fix than just flattening: resized to only cover the bottom third where its label actually lives, so the rest of the image keeps its full brightness instead of the whole card dimming uniformly just to darken one corner of it.

One technical wrinkle worth knowing about, found by actually testing in a real browser rather than assumed: `--glass-sheen` (used as a non-final layer in a stacked `background` in roughly 50 places across the app) briefly became a plain flat color during this pass - which is invalid CSS in that specific position. A plain color is only valid on the *last* layer of a multi-layer background; anywhere else, the entire background declaration gets silently dropped by the browser, not just that one layer. Every affected background would have quietly rendered with nothing behind it. Fixed by writing these as `linear-gradient()` calls with two identical color stops instead of a plain value - technically still the gradient function, but with no color transition between the stops, so nothing about the actual visual result is a gradient; it's the CSS-correct way to express "flat color, safely stacked."

Text selection and iOS's long-press copy/selection callout are disabled app-wide by default (meant to feel like an installed app, not a page of selectable text) - real `<input>`/`<textarea>` fields explicitly re-enable both, so typing, selecting, and copying what the person actually types (search bars, display name, etc.) still works normally.

**Full-bleed safe-area layout** — reverted. `viewport-fit=cover` was removed from the viewport meta tag, `apple-mobile-web-app-status-bar-style` went back to `default` from `black-translucent`, and every CSS rule that folded `env(safe-area-inset-*)` into its padding/positioning (page content, the bottom nav, modal header buttons, the offline banner, the error toast, NovaWrapped's slide panel, and a few others) was simplified back to its plain base value. The app no longer extends its background behind the Dynamic Island/notch/status bar or the home indicator area - content and background both stay within the standard safe rectangle, the same as before this work was ever done.

The bottom nav's specific glass treatment (`--glass-chrome-*` tokens) - genuinely see-through, a soft top-left highlight, a diffuse top-edge glow, no border, an elevation shadow instead of a ring - is the app's most refined version of the shared "Liquid Glass" language, and is what every other piece of this same chrome tier (the search bar, the segmented-toggle active state) is meant to match. The chrome tokens themselves are kept in exact sync with the nav bar's own blur/saturation values rather than being a separate, looser approximation of them. This tier is about the glass recipe, not whether something floats or sits flush - the nav bar itself floats, as a pill with margin on every side (see Bottom navigation above). Content-backing surfaces (cards, sheets, `--surface`) use a lighter, one-step-back general glass recipe (`--glass-blur`, `--glass-border`, `--glass-shadow`) - that's what gives this chrome tier a distinct, elevated feel instead of every surface in the app looking identical.

**Modal action rows** — Favorite/Add to List/Share on Details, Share on Episode, Backdrop/Share/Rename/Delete on List Detail, and so on, all live in a labeled `.modal-action-row` within the modal's own content now, not as icon-only buttons floating over a photo backdrop. That floating pattern went through two earlier iterations first - a horizontal row, then a vertical stack down the corner once it grew past 1-2 buttons (List Detail's five-button version was the tallest UI element in the app at roughly 230px) - before landing here. The real reason for the move: an icon-only circle reads reliably as "tappable, does X" on iOS specifically, where that's a familiar system convention, but this app runs on Android and desktop browsers too, where a bare icon doesn't carry the same built-in meaning. A label next to the icon removes the ambiguity entirely, at no cost to anyone who already recognized the icon. `flex-wrap` on the row means it holds up at any viewport width without horizontal scroll or JS-measured layout - four labeled chips wrap to a second line on a narrow phone exactly as gracefully as they'd sit on one line on a wider screen. Every modal's floating header (`.modal-header-nav`) now holds just Close, confirmed by checking every modal in the app individually rather than assuming - so the corner stays a single, consistent, always-reachable control regardless of how many other actions a given modal has, and those actions get proper labels in the content instead of being sized down to fit a shrinking corner. Details' own row specifically (exactly 3 chips) matches the equal-width 3-column grid directly below it (Watch/Trailer/Remove) via a `.modal-action-row-grid` modifier, rather than sizing to content like every other modal's row still does - those don't map cleanly onto a fixed 3-column grid the way exactly 3 items does.

**Every modal is full-screen now** — the five that were still `.modal-compact` (Episode Details, Choose an Avatar, the list backdrop picker, Reorder Lists, Add to List) all converted to the same full `.modal`/`.modal-sheet` every other modal in the app already used, for one consistent full-screen feel throughout rather than a mix of full-screen and centered-card styles. Content clearance below the header needed no extra work - four of the five already had the right padding class from their compact-modal days, and Episode Details has its own photo backdrop header so never needed it either way.

**Glass treatment unified across large surfaces** — `.confirm-card`, `.auth-overlay-card`, `.analytics-card`, `.hero-card`, and `.modal-sheet` each had their own slightly different hardcoded blur/saturation values (66px/270%, 64px/260%, 70px/230% respectively) instead of referencing the shared chrome token - close enough to look like they should already match, but not quite. All five now reference `--glass-chrome-blur` directly, which is confirmed genuinely theme-aware (300% saturate in light mode, 230% in dark, verified against `.bottom-nav`'s own explicitly-documented values, since that bar is the reference implementation the whole chrome tier is built to match). `.state-card` was found using a stale, unreduced `30px` blur left over from before `--glass-blur` itself was reduced to `12px` in an earlier pass - fixed to reference the token directly so it can't drift out of sync like that again.

The shared `--glass-blur` token itself (used by six other small-to-medium components across the app - Continue Watching's check button, the season rewatch button, confirm dialogs' Cancel button, a secondary auth button, and the base `.close-button`/`.action-button` styling) was also halved, from `blur(24px)` to `blur(12px)` - the same underlying issue as the header buttons above, just spread across more places than the one fix scoped to `.modal-header-nav` alone could reach. Left untouched: the larger, intentionally-strong blur values used for actual full-surface chrome (the nav bar, modal sheets, the dimmed backdrop behind a modal or confirm dialog) - a strong blur on a big surface reads as intended there, not as haze the way it does on a small circle.

## Cached identity on load

Firebase Auth restores its own signed-in session fast on reload, but the richer profile data (the real chosen avatar, the username, a display name that might differ from Auth's own) only ever arrives after an actual Firestore round trip - until that resolves, the avatar would show as a plain initial letter and the username line wouldn't show at all. The last-known real values (display name, avatar, username) are cached to localStorage every time they're confirmed from real data, and restored immediately on the very next app open - before Firebase Auth has even restored its session, let alone before Firestore responds - so the first paint already shows the right identity instead of a placeholder that corrects itself a moment later. Purely a faster first paint: the cache gets overwritten within moments by the real, authoritative data the same way it always has, so it can never meaningfully show something wrong for long. Cleared on sign-out, so a shared device never flashes the previous person's identity on the next person's first paint.

Reworked for more visual presence - a much larger logo (88px, up from 38px), bigger title type, and more generous spacing throughout the card, rather than everything compressed into a small centered box. Same underlying structure and glass card treatment as before (a proven, working pattern already consistent with the rest of the app), just scaled up to read as a deliberate, considered page rather than a compact form floating in empty space.

Brand images are hosted externally, not part of this repo - `NovaWatch.Logo.png` on the three auth screens (sign in, verify, choose username), `NovaWatch.AppIcon.png` for the Apple touch icon and every PWA manifest icon (including the maskable one, which reuses the same file rather than a dedicated inset variant), and `NovaWatch.FavIcon.png` for the actual browser favicon and one in-app settings icon. ## Dark mode

Genuinely darkened, not just "dark navy" - the base background moved from `#0a0d14` to `#050609`, and later to a fully neutral `#060606` once the whole app went monochrome (that `#050609` had kept a faint blue undertone deliberately, for the same "glass needs depth to read against" reason as below - the monochrome pass removed even that). Every dark-mode surface that used a plain dark-gray fill (the nav bar, confirm dialogs, the sign-in card, hero cards) had that gray darkened to match rather than being left sitting on top of a now-blacker page around it. Still not a flat `#000` - a true, fully neutral black makes translucent glass surfaces read as muddy and flat instead of luminous, since there's no depth in the base for the blur to show against. Every place that referenced an old base color value directly - two avatar badge cutout borders, the `theme-color` meta tag that colors the OS status bar to match - was updated too, so nothing was left mismatched against the current value.

## Load performance

The three Firebase SDK scripts used to load as plain, render-blocking `<script>` tags positioned even before the stylesheets - the browser couldn't discover the CSS, let alone paint anything, until all three had fully downloaded and executed in sequence from a third-party CDN. All three, and `app.js` itself, now load with `defer` instead - HTML guarantees deferred scripts execute in the order they appear in the document before `DOMContentLoaded`, so the same critical ordering (`app.js` calls `firebase.initializeApp()` at its own top level, so Firebase genuinely has to be ready first) is preserved exactly, while none of the four block the browser from parsing and rendering the rest of the page while they download.

## Beyond phones — tablet, desktop, and mouse input

`app.css` has three width-scoped rules at the very end of the file, in ascending order - everything above them is untouched below 600px, so phones get byte-for-byte the same CSS they always have. 768px (the tablet breakpoint) is comfortably above even the widest phone in portrait (a Pro Max is still only ~430px), so there's no risk of it firing on a large phone by mistake.

An intermediate `@media (min-width: 600px) and (max-width: 767px)` rule closes a real gap that existed between phone and tablet - `.app`'s own base max-width (600px) had already capped out below that range, but the tablet rule hadn't started yet, leaving visible empty space down both sides for a foldable unfolded, a small tablet in portrait, or just a desktop browser window resized to something in between. A modest bump to 680px there, not all the way to the tablet cap - that range reads as a wide phone, not a tablet, so it shouldn't suddenly jump to a tablet-scale layout.

Not a separate tablet layout - same bottom nav, same page structure, same components everywhere - just enough widening that an iPad doesn't get a stretched phone screen with dead space down both sides. `.app`'s content column widens to 1024px (the 12.9" iPad Pro's own portrait width - covers every common tablet in portrait completely; landscape on the largest tablets can still show some space by design, since going wider starts reading as a stretched desktop layout rather than a tablet one), the bottom nav widens to 620px to match without stretching its 4 buttons out to looking sparse, and the two real poster grids (`.library-grid`, `.poster-picker-grid`) gain a 4th column, since images benefit from the extra width in a way running text doesn't. Everything else - stat tiles, segmented toggles, modal action-button rows - stays exactly as it is, since their column counts are tied to a fixed number of items rather than to available space. That 1024px cap has no upper bound on when it stops applying, so it also covers genuinely wide desktop/laptop windows - content never actually stretches edge-to-edge on a 1920px monitor the way an unbounded mobile-first layout normally would.

**Mouse and pointer support, not just touch.** A global `[onclick]` rule gives every clickable element in the app - cards, list rows, toggle segments, anything that isn't a native `<button>`/`<a>` - a pointer cursor on hover, rather than the small handful of classes that had it explicitly before (native buttons/links get this from the browser automatically; plain `<div>`s with an onclick handler never did on their own). Scoped to exclude `.modal`/`.confirm-overlay` (their own onclick is only for detecting a tap on the backdrop to close, not a control in its own right) and `:disabled` elements (so a disabled button's own `cursor: not-allowed` isn't overridden by this broader rule's higher specificity). The main card types (`.card`, `.list-card`, `.continue-card`, `.search-card`) also get a real `:hover` state now - a small lift mirroring each card's own existing `:active` press-down, the other direction - scoped to `(hover: hover) and (pointer: fine)` specifically, not just `(hover: hover)` alone, so touch devices never match this at all and can't hit the classic mobile-web bug where a hover style gets stuck on an element after a tap.

**The TV Shows/Movies toggles are draggable now too** (Search, Upcoming) - the same drag-to-switch gesture the bottom nav bar already supported, generalized into a reusable function rather than copy-pasted. Simpler than the nav bar's own version in one real way: these toggles have no separate sliding pill of their own (each button just carries its own fill directly via its `.active` class), so there's no continuous element to visually drag - instead, whichever side the finger is currently over gets a live, purely-visual preview during the drag itself, with the real switch only actually committing once, on release.

The existing PWA install setup (`manifest.json`, the `apple-mobile-web-app-*` meta tags) already works identically on iPadOS's own "Add to Home Screen" - nothing further was needed there specifically for tablets to install and launch standalone the same way they do on iPhone.

Full-screen modals widen to match - `.modal` itself is `position: fixed; inset: 0`, spanning the true, uncapped viewport regardless of `.app`'s own width cap, so without this every modal (Settings, Details, NovaWrapped, Library's own "View All", every picker) would stretch wider than the tab content it was opened from on any screen wider than that cap. `.modal-sheet` now caps at 600px to match `.app`'s phone width, with the same 1024px tablet override, and `.modal` itself centers it via `justify-content: center` rather than letting it fill the full row by default. `.modal-sheet.modal-sheet-compact` (confirm-style dialogs, 460px) already wins over this via a more specific selector, so this only affects genuinely full-screen modals.

## Error toast

The one place a floating toast still exists in the app, deliberately narrow in scope: errors only. Success/confirmation messages stay silent, since they usually already come with a visible state change of their own (a screen transition, a button flipping to its done state) - a genuine failure with zero feedback is the actual problem silent toasts create, not a cosmetic one. Positioned above the floating nav bar (not at the bottom edge, not at the top - the offline banner already owns that space), using the same chrome-tier glass recipe as the nav bar and search bars. Auto-dismisses after 4.5 seconds, or on tap. A new error replaces whatever's currently showing rather than queueing - errors are rare enough now (roughly 40 real failure paths across the whole app, not everything that used to pass through the old toast system) that a queue isn't needed.

## Add to Home Screen prompt

Shown once, a couple seconds after the main app becomes visible for someone not already using the installed version - `isRunningStandalone()` (checking `display-mode: standalone` / `navigator.standalone`) is the one reliable, unspoofable signal available, and permanently suppresses the prompt for anyone it's true for. Everything else is the person self-reporting: there's no cross-platform event that fires when someone actually completes the manual iOS Share → Add to Home Screen flow, so "Added" can only ever be them confirming it, not the app verifying it. Instructions are platform-aware (Share sheet wording on iOS, browser-menu wording elsewhere). "Added" sets a permanent flag (never shown again on that device); "No thanks" - or tapping outside the dialog - only suppresses it for the current session, so a genuine next visit asks again rather than being silenced by one decline.

## Offline banner

Pinned to the top via `position: sticky`, not `fixed` - the difference matters here specifically: sticky still occupies real space in normal document flow while visible, so the app's own content (Home, Library, everywhere `.page` content lives) shifts down to make room for it rather than the banner floating over the top of whatever was already there. Only affects normal-flow content this way - other full-screen overlays in the app (the auth screen, modals) are `position: fixed` themselves, which by definition can't respond to a sibling's presence regardless of technique; those still just layer via z-index if the connection happens to drop while one's open.

## iOS keyboard scroll-hijack workaround

A still-current, longstanding WebKit bug (#191204): when the on-screen keyboard opens and the page has nothing left to scroll (an empty search results list, a library with only a few items, a short country list), iOS falls back to scrolling the raw document instead of absorbing the keyboard's own gesture internally - and while that fallback is active, the text caret gets computed against a desynced layout viewport and can land somewhere other than where the text actually is. Content-length dependent, which is why it read as intermittent rather than consistently broken. All 6 search inputs in the app (Search, both Library sub-tabs, both Upcoming sub-tabs, the region picker) give the page guaranteed extra scroll headroom only while actually focused, via a class toggled on `body` on focus/blur - not permanently, so a short page doesn't show a large empty gap under its own content the rest of the time. A separate, different caret bug (a backdrop-filter compositing quirk, always reproducible rather than content-dependent) was already fixed earlier on `.search-box` itself - both needed fixing, for different reasons.
