# NovaWatch

A mobile-first PWA for tracking TV shows and movies — search, add to a library, mark episodes/movies watched, log rewatches, and get release alerts. Built on Firebase (Auth + Firestore) and the TMDB API, with JustWatch-sourced "where to watch" availability.

Live at `https://www.novawatch.site/`. Mobile-first by design — phones get the primary, fully-tuned experience — but the goal is for it to look and work well wherever it's actually opened, not just on a phone; see Responsive design below for the full breakdown.

## Tech stack

- **Firebase Auth** — email/password and Google sign-in
- **Firestore** — the only backend; no server of NovaWatch's own
- **TMDB API** — search, metadata, episode/season data, recommendations
- **JustWatch (via TMDB)** — streaming availability by region
- **TVmaze API** — real per-episode broadcast/cable airtimes, used for TV episode release timing (see the TV episode release timing feature entry below). No API key required. Not used for streaming shows - see that entry for why.

### Firebase plan

Currently on the free **Spark** plan. This is a real constraint on the feature set: Spark doesn't include Cloud Storage, which is why avatars are a curated set of 8 hosted images rather than user uploads. Anything that needs Storage stays deferred until there's a reason to move to the paid Blaze plan.

### Data model

- `users/{uid}` — profile doc: `profiles` (array, currently always a single entry), `activeProfileId`, `region`, `username`, `timeZone` (the account's IANA timezone, refreshed on every profile save — see `send-release-notifications.js`)
- `users/{uid}/library/{itemId}` — each tracked movie/TV show
- `users/{uid}/archivedShows/{slug}` — shows removed from the library but kept for history purposes
- `users/{uid}/_internal/{lastStreakReminder|lastContinueWatchingReminder|notifiedReleases}` — small dedup docs written server-side only, by `send-release-notifications.js`, never read or written from the client. Cleaned up alongside `library`/`archivedShows` on account deletion (`deleteAllUserData`) — easy to miss when auditing account deletion from the client code alone, since nothing in `app.js` itself ever touches this collection.
- `usernames/{lowercased-username}` — `{uid, username}` reservation docs, used to enforce unique usernames (see below)

**Security rules** live in their own document, `firestore-rules.md`, kept up to date separately from this file — check there for the current recommended ruleset and whether it's actually been applied in the Firebase console yet.

## Core features

**Library & search** — TMDB-backed search; add movies/TV shows; mark watched with a single tap (no rating/reaction popup in the way).

**Rewatch tracking** — per-episode for TV, per-title for movies, via a tap-to-manage popup (Add/Remove Rewatch) rather than a one-way counter. Unwatching something clears its rewatch history. A season can also be bulk-rewatched (or have its rewatches cleared) once every released episode in it has been watched at least once — gated behind a long-press on that season's tab, or the "Mark All Episodes Watched" button for the whole show at once.

**Opening a TV show's details** — lands on the season containing the next released-but-unwatched episode (`getCurrentSeasonForShow`) and auto-scrolls the episode list straight to that row, rather than opening at the top of Season 1 and leaving the person to hunt for where they left off. A caught-up show lands on the season of its most recently watched episode instead. A show with nothing released and unwatched yet (nothing to scroll to) simply opens at the top, same as it always did.

**Marking a later episode watched** — if opening an episode directly (say S2E6) and marking it watched would leave earlier released episodes in the same show still unwatched (`getEarlierUnwatchedEpisodes`), a themed confirm dialog offers to mark those watched too in the same action, rather than silently leaving a gap. Only fires when marking watched, never when un-watching one - removing a single episode's watched status is always exactly what it looks like, nothing to ask about. Declining, or tapping outside the dialog, marks just the one episode that was actually tapped.

**Discover → For You** — TMDB `/recommendations` seeded from your library (the 5 highest-rated/most-recently-added items of that type), ranked by cross-seed hit count then TMDB score. Falls back to plain Trending when the library's empty for that content type. A large library can genuinely exhaust its own recommendations - if most of what TMDB would suggest for your top-rated shows is something you've already added, there's only a handful of actually-new picks left, which reads as a mostly-empty page on a wide screen rather than a personalized one. Padded out with current trending titles (deduped against both the library and what's already ranked) up to a minimum of 12 results whenever the real recommendation count falls short - a real fallback, not a relabeling of the results as something they're not.

**Continue Watching** (Home) — the next unwatched episode for every in-progress show, plus any unwatched movies. Swipeable: right reveals "mark watched", left reveals "remove" (or "stop watching" for a TV show with progress already logged, which keeps its watch history instead of deleting it). Marking an episode watched this way also shows how many episodes are left in that show, if any.

**TV episode release timing** — every episode carries a real release instant again, timezone-correct for every viewer. This was fully removed at one point (see the git history of this file for that saga) after a long series of attempts kept surfacing new edge cases. Brought back deliberately differently: rather than one formula trying to cover every show, each episode is anchored one of two ways -
- **Broadcast/cable shows** — a real, network-announced local airtime from TVmaze, when TVmaze lists the show under a real `network` (not a `webChannel`). Converted DST-aware via the same `getTimezoneAnchorUTC` helper movies already used, just pointed at the network's own timezone instead of always Pacific.
- **Everything else** (streaming, or no TVmaze match at all) — the same midnight-Pacific streaming convention movies use. Deliberately the *latest* time in the range real streaming platforms actually use (official Netflix/Disney+ policy; most others release earlier in the evening PT), so this can under-promise (show "not released yet" for a few extra hours on an early-release platform) but never over-promise (claim something's out before it verifiably is, anywhere).

Only the calendar DATE this produces is meant to be trusted per viewer timezone - not the exact hour. `isReleased()` does an exact-instant comparison (not a calendar-day one), so a not-yet-released episode can't be marked watched, doesn't count toward Library/Continue Watching progress, and shows a countdown instead of "Unwatched" in the episode list and details modal. Anywhere a release date is shown as part of a longer meta line (the movie/episode details modals), `formatReleaseDescription()` pairs the real calendar date with that same friendly countdown - "Aug 14, 2026 · In 3 days" - once released, it's just the plain date again. A standalone badge or caption that already has its own context (the Upcoming tab's cards, the episode list rows) still uses the countdown alone via `getCountdown()`. A Library grid card for a Coming Soon item (`getCardReleaseDate()` - a movie's own `releaseDate`, or a TV show's earliest not-yet-aired episode) gets the same `formatReleaseDescription()` treatment as a `title` attribute on the card itself, rather than a visible badge over the poster - deliberately non-intrusive, since only a handful of cards in any given grid actually need it. TVmaze resolution (`resolveTVmazeShow`) is cached per show on `tvmazeId` so a show only gets searched for once; a show TVmaze doesn't have just stays on the streaming default, same as every show did before this feature existed - never a hard failure. Movies are unaffected — same convention as before.

**Content rating** — PG-13, TV-MA, etc., shown as a badge in the details modal for both movies and TV shows. Fetched from a separate per-region TMDB endpoint (`release_dates` for movies, `content_ratings` for TV), tried in the viewer's own streaming region first, falling back to US.

**Collection/franchise info** — for movies that TMDB has flagged as belonging to a collection (e.g. "Part of The Dark Knight Collection"), shown in the details modal. Movie-only; TV doesn't have an equivalent concept in TMDB. Informational only - there is no in-app nudge toward the next film in a collection (there briefly was; it went when in-app notifications were removed entirely).

**Viewing Analytics** (Home) — total watch time (including rewatch passes), with a current-streak badge underneath it (consecutive calendar days with at least one watch/rewatch logged - resets to zero the moment a day is missed, distinct from the all-time-record "longest streak" the streak achievements track - lit orange while live, a neutral muted pill when there's no active streak), and counts of watched movies/shows/episodes/rewatches in the tile grid below. Sits below Continue Watching, not above it - the thing you actually act on (what to watch next) leads; stats and streaks are motivating, but secondary to that.

**Achievements** — computed client-side from library data on every load, not stored as separate synced records; only the small "which ones are unlocked" array is persisted. Bidirectional — unwatching something can revoke an achievement it had unlocked, not just grant new ones. Recomputed as part of `refreshActivePage()` (debounced via `checkAchievements()`), so the unlocked count in Settings is always current the moment the app loads or anything changes — no need to open the Achievements screen first to see it refresh. All 22 achievements in the flat `ACHIEVEMENTS` list are unlockable by everyone — no tiers, no gating. They cover movies/shows/episodes watched at several thresholds, watch streaks, rewatch counts, a full-season rewatch, library size (`Collector`), variety (`Well-Rounded Viewer`), timing (`Night Owl`), and completion speed (`Speed Run`, `Binge Finisher`, `Big Binge`, `The Comeback`). Each entry carries its own small stroke icon (a set of shared constants — `ICON_FILM`, `ICON_TV`, `ICON_FLAME`, etc. — reused across achievements in the same family, e.g. every movie-count milestone shares the film icon) rather than one identical medal icon for all of them, so the list stays scannable given how long it is.

**Sharing** — deep links for a show/movie (`?share_type=tv|movie&share_id=<tmdbId>`) or a single episode (`?share_type=episode&share_id=<showTmdbId>&share_ep=<sXeY>`). Opening a shared episode link loads the parent show first, then drills into that specific episode.

**Unique usernames & display names** — every account reserves a unique, lowercase-only username (`[a-z0-9._]`, 3–20 characters), chosen at signup or via a blocking "Choose a username" screen for Google sign-in / any pre-existing account without one. Separate from that is a freely-editable **display name**, shown everywhere in the UI instead of the username — both are visible together in Settings (`Display Name` / `@username`). See `firestore-rules.md` for how username uniqueness is actually enforced.

**Auth flow feedback** — sign-in, sign-up, Google sign-in, password reset, and account deletion all show errors and confirmations inline, in the form itself (red for errors, green for the couple of confirmations with no other visible state change, like a password reset email) - not via a toast, since toasts don't exist in this app. This matters more here than almost anywhere else in the app: a validation error with no visible feedback at all (a blank email field, a wrong password) would otherwise leave someone tapping a button that does nothing, with no way to tell why.

**Settings** — reachable via the button on Home's identity card, which becomes a close (X) button while Settings is open. Organized into two sections: **Preferences** (appearance, streaming region, notifications) and **Library** (Library Display, achievements) — plus NovaWrapped, sign-out, account deletion, and Privacy & Terms below those. Structurally matches every other tab (same padding, same section-title sizing, same spacing rhythm) rather than being a visually separate design.

**Streaming region** — a full ISO 3166-1 country picker, still fully manual and editable at any time; auto-detected on first sign-in via the browser's real Geolocation API (reverse-geocoded to a country through a free client-side lookup) when available and granted, falling back to a locale-string guess for every failure mode - no geolocation support, permission denied, a timed-out/failed lookup, or an unsupported country. Drives which "where to watch" info TMDB/JustWatch returns.

**Dark mode** — a three-way Light/Dark/Auto toggle in Settings. Saved to `localStorage` (device-level, not synced across devices) and applied before first paint via an inline script in each page's `<head>`, so there's no light-then-dark flash. Auto follows the OS setting live via a `matchMedia` listener.

**Notifications** — real push, delivered even when the app is fully closed, via OneSignal (`ONESIGNAL_APP_ID` in `scripts/app.js`, inert until that's actually configured - see `PUSH_NOTIFICATIONS_SETUP.md`). The only notification delivery mechanism in the app - a single on/off toggle in Settings ("Stay in the loop"), no per-category selection, and no separate client-side path that fires while the app happens to be open. The client only handles subscribing a device and requesting permission (which OneSignal's own subscription flow needs regardless of who triggers a send) and tying that device to the signed-in account; a separate server-side script (`send-release-notifications.js`, not loaded by the app) does the actual "what to send, to whom, today" decision on a schedule, since a closed browser tab can't run anything itself. Never at the moment TMDB/TVmaze data merely mentions something, and never for episodes that were already out when a show was added, since a freshly-added show's full episode list is already in hand at add time. One combined notification per account per day covering everything releasing, not one push per release (see the APNs store-and-forward comment in the script for why) - the title is "New Release" for exactly one, otherwise "N New Releases Today". The body (`buildReleaseLabels`) groups multiple episodes of the *same* show and season into one line rather than repeating the show name per episode - "Adults - Season 2 Episodes 3-4" instead of "Adults - Season 2 Episode 3 release; Adults - Season 2 Episode 4 release" for a double-episode drop - falling back to a plain comma list ("Episodes 3, 6") on a genuinely non-consecutive set rather than misrepresenting it as a range. Premieres, regular episodes, and movies are never grouped into each other's lines, and always appear in that order - a premiere is the most likely thing worth noticing first, movies the least time-sensitive (an episode keeps sliding further behind the longer it's ignored; a movie doesn't). Longer than 3 lines truncates to "and N more" (counting lines after grouping, not raw releases). The "Stay in the loop" button, and every other on/off-style status in the app (Library Display), share one green (on/enabled) / red (off/blocked) visual language - a device that can't support notifications at all shows a neutral muted state instead of red, since that's a device limitation, not something the person chose to turn off.

**Engagement reminders** — a streak reminder and a Continue Watching reminder, each only ever checked on a day when nothing in the library is actually releasing (never alongside a real release notification). The streak reminder fires once, only when a real streak built from watching yesterday hasn't been extended yet today. The Continue Watching reminder now names a specific, randomly-picked item - a TV show's actual next episode (the same "lowest season, then lowest episode number, among released-and-unwatched" rule the app's own Continue Watching row uses, so it always matches what the app itself would show as next), or an unwatched movie - rather than a generic "you have something waiting," and fires only after 3+ days of no watch activity at all, with its own separate 7-day cooldown once sent, so a quiet stretch reads as an occasional nudge rather than a daily one. Both run entirely server-side, sharing the same UTC-based watch-date data movies/episodes already use for the streak achievement and the Home tab's Current Streak badge. Two separate scheduled runs, not one - release notifications and engagement reminders fire at different times of day on purpose, not just because they're logically distinct: keeping real separation between the two means a "watch something today" reminder doesn't compete for attention with the same morning release check, and lands at a point in the day someone's meaningfully more likely to actually be looking at their phone than at 08:00 sharp. Every account is still processed on the same single pass for whichever concern that particular run covers, so the actual local time either kind of notification arrives at still depends on how far an account's timezone sits from whichever UTC anchor that run uses. OneSignal push is the only notification mechanism in the app - no separate in-app log or list of past notifications.

**Library Display** (Settings) — Finished, Unwatched, and Stopped Watching (the three TV Library categories that hide content the person is done with, hasn't started, or chose to stop, one way or another) can each be shown or hidden independently - on (green) by default, off (red) once the person turns one off. Purely a display filter - hiding a category never touches the underlying watched/stopped data, it just skips rendering that category block.

**Avatars** — 8 curated hosted images, assigned at random to a new account and always changeable via the picker in Settings.

**PWA install shortcuts** — long-pressing the installed app's icon offers Discover/Library/Upcoming as direct shortcuts (Home is skipped, since it's already the default landing).

**Upcoming** (4th bottom-nav tab) — every not-yet-released movie and TV episode from the library (every queued-up episode per show, not just the next one). Same structure as Library: a TV Shows/Movies segmented toggle (`setUpcomingView`), the same search box per sub-view (filters by title, same debounce), each sub-view rendered with the exact same category-block/poster-grid card component Library uses (including the same long-press-to-change-poster gesture, since these are already-tracked library items), just bucketed by Today/Tomorrow/This Week/Later instead of watch status. Each card adds one single-line caption under the title (season/episode + countdown, or just the countdown for movies) since an upcoming item needs its release status spelled out in a way an already-added Library item doesn't. Tapping a card opens the usual details modal.

**Bottom navigation** — a floating "Liquid Glass" pill bar, 4 tabs (Home/Discover/Library/Upcoming). An edge-to-edge, flush-to-the-bottom version was tried and reverted after not looking right on real devices - back to the original floating pill, with margin on every side. Supports both tapping a tab and dragging a finger across the bar to switch tabs, with the pill indicator tracking the finger continuously during a drag and settling into place on release. The indicator measures whichever button is active at render time, so it isn't hardcoded to any particular tab count.

**Change-aware list rendering** — Library, Continue Watching, and the episode list inside a show's details modal only touch the DOM when their content has genuinely changed, rather than rebuilding on every periodic background sync (or every time the modal refreshes) regardless. Rebuilding unconditionally was destroying and recreating every poster/thumbnail/episode-still image element each time, which read as flashing even though nothing had actually changed.

## NovaWrapped

A Spotify-Wrapped-style yearly recap, gated to release **January 1, 2027** — before that date, tapping its "View" button in Settings shows an error toast explaining when it opens. The `novawatch` account (the developer's own) can preview it early regardless of the date - a plain client-side check against that account's own username, not a Firestore rules change, since it's reading data the signed-in account already legitimately has access to. Lives as a modal (`#novaWrappedModal`), not a separate page, so it shares the same signed-in session's data as the rest of the app instead of loading a second copy of the Firebase SDK.

Picking a year lands on a full-screen, story-style slideshow - tap through (or tap the left/right edge of the screen, the same interaction as Instagram/Snapchat stories), with a progress bar across the top. Each slide gets its own vivid, saturated gradient background, deliberately more dramatic than the rest of the app's subtle glass language - a recap is meant to feel like a celebration, not another settings screen. The sequence: total watch time (the big hero number) → movies → TV episodes/shows → the most-watched show (its real poster blurred into the slide's own background) → busiest month → rewatches → a final recap card summarizing everything at once, with a real Share button. A slide only exists if there's actually something to say for it - a year with no rewatches simply has no rewatch slide, rather than a hollow "0 rewatches."

Tracks January 1 – December 31 UTC, with a 7-day grace period after account creation excluded (so bulk-adding existing watch history right after signing up doesn't count as binge-watching). Rewatches get their own dedicated slide as a fun fact, but are still deliberately **excluded** from the main Total Watch Time hero number, unlike Home's Viewing Analytics, which deliberately *does* count them toward its own total — that inconsistency between the two is intentional, not a bug.

## Design system

`tokens.css` defines the shared "Liquid Glass" visual language — translucent, blurred, low-opacity surfaces with a soft diagonal sheen — used consistently across the whole app (cards, sheets, buttons, the search bars, the bottom nav) rather than each surface inventing its own treatment. A defined corner-radius scale (`--radius-xs` through `--radius-2xl`) assigns a consistent roundness by component role — e.g. every poster thumbnail across every tab uses the same radius, regardless of which screen it appears on.

The blue accent (`--blue: #006aff`, `--blue-light: #00faff`, used for `--blue-dark`/`--flat-blue` too) is the same pair of exact values in both light and dark mode now, rather than a separate, lighter set for dark backgrounds the way it used to shift - both already have enough contrast to stay legible either way. `--blue-gradient` inherits `--blue` automatically since it's defined as `var(--blue)`, not a separate hardcoded value (see the token's own comment for why - it was flattened from a two-tone gradient to solid a few rounds back). The one place this couldn't be a CSS variable: box-shadow/glow colors that need their own alpha channel (`rgba(0, 106, 255, 0.3)` and similar, scattered through `app.css`) - custom properties can't be interpolated inside `rgba()`'s color channels, so these are `--blue`'s RGB value hardcoded as a literal triplet, kept in sync by hand whenever the token itself changes.

Text selection and iOS's long-press copy/selection callout are disabled app-wide by default (meant to feel like an installed app, not a page of selectable text) - real `<input>`/`<textarea>` fields explicitly re-enable both, so typing, selecting, and copying what the person actually types (search bars, display name, etc.) still works normally.

**Full-bleed safe-area layout** — the installed PWA's background extends behind the Dynamic Island/notch/status bar and the home indicator/gesture area on every device, rather than the OS's own background color showing through a gap (the `viewport-fit=cover` viewport meta tag is what actually enables this - without it, `env(safe-area-inset-*)` values are meaningless and the whole layout stays confined to the safe rectangle). Only the background is full-bleed; actual content (page padding, the bottom nav, floating modal close buttons) folds the real device inset into its existing spacing so nothing sits under a cutout or gesture area. `env(...)` resolves to `0px` on devices/browsers with no safe area (most Android phones, desktop), so this has no effect there.

The bottom nav's specific glass treatment (`--glass-chrome-*` tokens) - genuinely see-through, a soft top-left highlight, a diffuse top-edge glow, no border, an elevation shadow instead of a ring - is the app's most refined version of the shared "Liquid Glass" language, and is what every other piece of this same chrome tier (the search bar, the segmented-toggle active state) is meant to match. The chrome tokens themselves are kept in exact sync with the nav bar's own blur/saturation values rather than being a separate, looser approximation of them. This tier is about the glass recipe, not whether something floats or sits flush - the nav bar itself floats, as a pill with margin on every side (see Bottom navigation above). Content-backing surfaces (cards, sheets, `--surface`) use a lighter, one-step-back general glass recipe (`--glass-blur`, `--glass-border`, `--glass-shadow`) - that's what gives this chrome tier a distinct, elevated feel instead of every surface in the app looking identical.

## Cached identity on load

Firebase Auth restores its own signed-in session fast on reload, but the richer profile data (the real chosen avatar, the username, a display name that might differ from Auth's own) only ever arrives after an actual Firestore round trip - until that resolves, the avatar would show as a plain initial letter and the username line wouldn't show at all. The last-known real values (display name, avatar, username) are cached to localStorage every time they're confirmed from real data, and restored immediately on the very next app open - before Firebase Auth has even restored its session, let alone before Firestore responds - so the first paint already shows the right identity instead of a placeholder that corrects itself a moment later. Purely a faster first paint: the cache gets overwritten within moments by the real, authoritative data the same way it always has, so it can never meaningfully show something wrong for long. Cleared on sign-out, so a shared device never flashes the previous person's identity on the next person's first paint.

## Load performance

The three Firebase SDK scripts used to load as plain, render-blocking `<script>` tags positioned even before the stylesheets - the browser couldn't discover the CSS, let alone paint anything, until all three had fully downloaded and executed in sequence from a third-party CDN. All three, and `app.js` itself, now load with `defer` instead - HTML guarantees deferred scripts execute in the order they appear in the document before `DOMContentLoaded`, so the same critical ordering (`app.js` calls `firebase.initializeApp()` at its own top level, so Firebase genuinely has to be ready first) is preserved exactly, while none of the four block the browser from parsing and rendering the rest of the page while they download.

## Data export

**Export My Data** (Settings → Account) downloads the full library - every title, per-episode watched flags, watch dates and rewatch counts - plus account-level settings, as a versioned JSON file (`exportFormatVersion: 1`, so a future importer can tell which shape it's reading). Entirely client-side: `state.library` is already fully in memory via the `onSnapshot` listener, so this costs **zero additional Firestore reads** regardless of library size. Exists because a library of a few thousand tracked episodes is real investment, and until this the only way out was account deletion, which destroys it.

## Notification subscription mirror & the read-quota problem

`state.notificationsEnabled` mirrors OneSignal's own push-subscription state into the Firestore profile doc (`syncNotificationsEnabledFlag`, called from OneSignal's `change` listener and once after sign-in to backfill existing accounts). It is **never** the authority on delivery - OneSignal remains that - and is deliberately best-effort, since a failed write costs one unnecessary library read on the next run and nothing more.

It exists purely to fix the single worst scaling cost in the project. `send-release-notifications.js` previously read *every* account's *entire* library on *every* run, unconditionally, twice daily, just to find the few accounts with something releasing. At a ~120-item library that's ~120 document reads per account per run (~240/day), which exhausts Firestore Spark's 50,000 daily read quota at roughly **200 accounts** - before anyone even opens the app, and app usage itself does a full library read per sign-in. When a Spark project hits that ceiling, reads start failing for everyone until midnight Pacific.

The job now skips any account whose `notificationsEnabled` is explicitly `false`, turning it from O(all accounts) into O(subscribed accounts). Checked against `=== false` specifically, not falsiness: an account whose profile doc predates the field has `undefined` and is still scanned, so nobody silently stops receiving notifications when this ships - those accounts self-correct the next time the app is opened.

## Smoke tests

`smoke-tests.js` (run `npm test`, or `node smoke-tests.js`) covers the pure logic the app's core guarantees rest on: `isReleased`, `getAvailableEpisodes`, `getTVProgress`, `getNextUnwatchedEpisode`, `getEarlierUnwatchedEpisodes`, `isTVUpToDate`/`isTVFinished`, `getCurrentWatchStreak`, and `localDateStringToISO`. 28 assertions; exits non-zero on failure so it works as a pre-deploy gate.

It extracts those functions by source text from the real `app.js` and evaluates them in isolation, rather than importing - `app.js` is a classic browser script that touches `document`/`window` at load, and refactoring 8,500 working lines purely to make them importable would be a large, risky change for a test file. Extraction fails loudly if a function is renamed, rather than silently passing.

This complements the existing structural validation (syntax parse, brace/tag balance, duplicate-symbol scans, handler resolution) rather than replacing it: those prove the file loads and is intact, but cannot catch a logic regression - "marking an episode watched stopped counting toward progress" parses perfectly.

## Continue Watching art

Each card leads with the **episode's own still** (`ep.still`), falling back to the title's backdrop, then its poster. It used to render the show's poster shrunk to 80x116 - the same portrait thumbnail already shown throughout Library - which used the richest asset the app has in its least effective form and told you nothing about the specific episode you were about to watch.

The frame is now 150px wide at 16:9 (`.continue-poster`), which is *more* image area than the old poster while taking *less* vertical space, so cards get shorter and more of the list fits on screen. A poster used as final fallback (an unaired episode with no still, on a title with no backdrop) gets `.is-poster` → `object-fit: contain`, so a portrait image isn't sliced to fill a landscape frame. `.skeleton-row-thumb` tracks these dimensions exactly - any mismatch shows up as a visible jump the moment real content replaces the placeholder.

## Typography

Two type roles, deliberately separated. UI chrome - buttons, labels, nav, stats, settings rows - stays on the system stack (`-apple-system`/`SF Pro`/`Inter`), so it feels native to the device and renders instantly. **Titles of works** - show names, movie names, episode names, and the details-modal headline - use `--font-title` (Newsreader, a serif) instead.

The split is the point: naming a work is a different job from labelling a control. A serif there reads the way a film-credit block or a criticism byline does, and it's the cheapest single change that stops the app looking like every other system-font app. Scoped to `.card-title`, `.search-card-title`, `.continue-title`, `.continue-episode-name` (italic, to separate it from the show name above without another size or colour step), `.modal-title` and `.episode-title` - nothing else.

Weights and tracking are re-tuned per role rather than inherited: the sans needed 700-800 with negative letter-spacing to hold together at small sizes; a serif given the same treatment looks clotted, so these sit at 500-600 with neutral tracking and slightly larger sizes to compensate for the smaller x-height. Loaded with `display=swap` and real serif fallbacks (Iowan Old Style, Palatino, Georgia), so a slow or failed font load degrades to the right *kind* of type rather than back to sans - and because chrome never depends on it, a font stall can't delay a single control. Deliberately not precached by the service worker: offline, the fallbacks handle it, and precaching a third-party stylesheet would add a failure point for no real gain.

## Viewing Analytics - no nested cards

The four stat cells (`.stat`) have no fill, border, shadow or radius of their own. They used to be cards, inside the analytics card, inside the page - three levels of near-identical elevation, which makes depth stop meaning anything. They now sit directly on the analytics surface, separated by hairlines drawn per-cell (`:nth-child(odd)::after` for the vertical rule, `:nth-child(-n+2)::before` for the horizontal one) rather than a border on every cell, so the grid never doubles a line or draws one along its own outer edge. `#dashboardStats.stats` sets `gap: 0` for the same reason - a gutter would break the hairlines into floating segments. Scoped to `#dashboardStats` specifically, because NovaWrapped's recap reuses the same `.stats` layout and does still want real tiles with gutters. The coloured icon badges are left as the only filled elements, so they carry the visual weight alone.

## Responsive design

Eight breakpoints in `app.css`, each targeting a real device/situation rather than an arbitrary width, plus a separate query matched against input capability rather than screen size. Nothing below 768px is touched by any of the wider-screen blocks, and nothing above 1279px is touched by the compact/short blocks — a phone held normally only ever sees the base styles it always has.

`.app` itself (the content column all four main tabs and the bottom nav sit in) has no width cap at any of these tiers, or at the base size below them either — it's `width: 100%` unconditionally, the exact same relationship to the viewport `.modal` already has (`position: fixed; inset: 0`, also uncapped). This used to progressively cap wider at each tier below, the same conservative instinct that originally kept poster grids and modal content narrow too - but `.modal-content` and `.empty-state` (see both below) already independently cap their own *reading* width regardless of how wide their container is, so there was no remaining reason for `.app` itself to stay narrow as well, any more than there'd be a reason for `.modal` to. `.page`'s own padding (18px each side, plus safe-area insets) provides the same breathing room from the true screen edge that `.modal-content`'s own padding already gives an edge-to-edge modal.

- **Tablet** (`min-width: 768px`) - not a separate tablet layout, same bottom nav/page structure/components everywhere, just enough widening elsewhere that an iPad doesn't get 4-column poster grids sized for a phone. The bottom nav widens to 620px so its 4 buttons don't look sparse, and `.library-grid`/`.poster-picker-grid` gain a 4th column since images benefit from the extra width in a way running text doesn't.
- **Large screens** (`min-width: 1280px`) - a laptop/desktop window, or a large tablet in landscape (a 12.9" iPad Pro is ~1366px there). More breathing room for the nav bar (680px) and a 5th poster-grid column now that there's room for it.
- **Large desktop monitors** (`min-width: 1600px`, then `min-width: 2000px`) - two further steps so a real external monitor doesn't just freeze at the 1280px block's own nav/grid sizing forever. 1600px covers common laptop/external-monitor widths (nav to 760px, 6 poster-grid columns); 2000px covers 4K/ultrawide monitors specifically (nav to 820px, 7 columns).
- **Compact phones** (`max-width: 359px`) - an iPhone SE, budget/older Android phones, and a folding phone's own cover screen (as narrow as ~280px on a Galaxy Z Fold). The base 3-column poster grid starts working against itself below this width - each poster gets so little room the title/year underneath wraps awkwardly - so this drops to 2 columns and trims `.page`'s horizontal padding slightly.
- **Short/landscape viewports** (`max-height: 500px`) - matched on available height, not width or orientation, so it correctly covers a phone rotated to landscape (the main real case) without ever firing on a phone held normally (even the shortest common phone is 667px tall in portrait). The bottom nav and the details-modal backdrop image are both sized for portrait's much larger vertical budget - left alone, either one alone can eat a third or more of a short landscape viewport before any content shows, so both shrink here, along with the auth screen's own padding.
- **Fine-pointer hover** (`(hover: hover) and (pointer: fine)`) - matched against actual input capability, not screen width, since a wide viewport doesn't imply a mouse (a tablet in landscape is still touch-only) and a mouse doesn't imply a wide viewport (a small laptop window is still a mouse). This is also what avoids the classic "sticky hover" bug on touch devices, where a tap can trigger a `:hover` state with nothing to un-trigger it - these rules simply never match on a device that can't truly hover. Adds subtle lift/glow feedback (never a color or layout change) to cards, nav buttons, the empty-state CTA, season buttons, and settings rows - the same "this is interactive" cue `:active` already gives touch, for a pointer that can hover before it ever clicks anything.
- **Reduced motion** (`prefers-reduced-motion: reduce`) - two separate blocks disabling non-essential animation for anyone whose OS/browser has this set.

The existing PWA install setup (`manifest.json`, the `apple-mobile-web-app-*` meta tags, `viewport-fit=cover`) already works identically on iPadOS's own "Add to Home Screen" - nothing further was needed there specifically for tablets to install and launch standalone the same way they do on iPhone.

`.modal-content` (the shared wrapper for every full-screen modal's actual content - show/episode details, Settings, Achievements, Library Display, the region picker) gets its own `max-width: 720px` cap starting at the 768px tablet block, held fixed through every wider block above it rather than growing further with them. `.modal` itself is a separate fixed, full-viewport overlay (`inset: 0`) with no width cap of its own, so without this, a synopsis paragraph or a row of settings could stretch to the full width of whatever block currently applies - genuinely harder to read at 100+ characters per line, not easier, and a settings row that wide just leaves its icon and label bunched on the left with empty space trailing off to the right.

`.modal-backdrop-header` (the hero image above it) is left full-bleed rather than capped to the same 720px - a wide photo is a fine, normal pattern, unlike a paragraph or a list. Its *height* needed its own fix here, though: fixed at a flat 240px regardless of width, `background-size: cover` cropped a progressively larger share of the actual image away as the box got wider with nothing to compensate - fine on a phone (~2.5:1), but a real problem once `.app` itself was scaling up to 1480px wide with the same 240px height (~6:1) - cover crops to fill the box, so at that ratio it was cutting away most of a poster's actual subject just to fill an increasingly short, wide strip. Height now scales up alongside each of the four wider blocks (280px → 320px → 360px → 400px) to keep the crop at roughly the same reasonable ratio the design was actually tuned around, instead of degrading further the wider the screen gets.

`.continue-group` (Continue Watching's own cards on Home) gets the same treatment for a different reason - each card is a swipeable list ROW (a fixed-width 16:9 episode still plus a text block that fills whatever's left), built for one narrow column, so simply letting `.app` keep growing wider just stretched each card's own description further rather than showing anything new. Switches to a 2-column grid starting at the 768px tablet block (an iPad in portrait already has plenty of room for two), 3 columns at 2000px, so the extra width goes toward showing more shows at once instead. `.continue-card-wrap`'s own existing `margin-bottom` still spaces rows vertically within a column; only `column-gap` is added for the horizontal gap between columns, and each group's title (`.continue-group-title`) spans both/all columns as one heading above them rather than getting squeezed into the first. The loading skeleton (`skeletonRows()`, shown while `!libraryLoaded`) is wrapped in its own `.continue-group` div for this specific container - without it, the skeleton would stay single-column at these widths while the real content "pops" into 2-3 columns the moment it actually arrives, since the grid CSS is scoped to the class, not the container itself.

`.search-results-grid` (Discover's search results and For You recommendations - `#searchResultsList`) gets the identical 2-column/3-column treatment at the same breakpoints, for the identical reason - `.search-card` is the same "fixed poster + a text block that fills whatever's left" row shape as `.continue-card`. Unlike `.continue-card-wrap`, a `.search-card` has no margin of its own for vertical spacing between rows (adjacent cards just relied on normal block-flow stacking before this), so a small row gap is added alongside the column gap here rather than relying on a margin that doesn't exist. This container already carries its grid class directly (rather than a child wrapper the way Continue Watching's groups do), so its own loading skeleton needs no special wrapping - inserting skeleton rows straight into it already picks up the grid correctly.

`#dashboardStats.stats` (Home's Viewing Analytics tiles) switches from a 2x2 square to one row of 4 starting at the 768px tablet block - each tile only holds a short number and a label, so even at a quarter of a 1024px+ column each tile has at least as much room as the mobile 2-column version ever did; there was no reason left for it to stay square once there was space for a row. `.empty-state` (the "You're All Caught Up"/"Cleared Your Watchlist"-style placeholder, wherever a grid has nothing to show) gets a flat `max-width: 480px` and `margin: 0 auto` unconditionally, not scoped to any breakpoint - its `grid-column: 1/-1` already makes it span however many columns its parent grid currently has, which was harmless on a phone (already narrower than the cap) but meant one small centered icon and a line of text stretching across 2-3 whole poster columns' worth of width on any of the wider tiers.

Not everything here should scale, and a few things deliberately don't, on purpose rather than by omission: `.confirm-card` (Delete Account, rewatch popups, the mark-previous-episodes prompt, Add to Home Screen) stays a flat 340px at every width, the same way a native OS alert dialog would - a decision-point dialog isn't meant to grow just because the monitor did. `.auth-overlay-card` stays 400px for the same reason - a sign-in form filling a desktop monitor wouldn't read as more usable, just stranger. `.wrapped-slide-content` (NovaWrapped's own slide text) stays a fixed 380px column on purpose - it's built as a phone-shaped "story" (the same Instagram/Snapchat-style format the rest of NovaWrapped already commits to, see NovaWrapped above), and widening that column on desktop would work against the format it's deliberately imitating, not for it. The horizontal-scrolling Discover carousel and season-tab rows don't need width rules at all - a scrollable row simply shows more or fewer fixed-width items depending on space, which already is the correct adaptation for that shape.

## Error toast

The one place a floating toast still exists in the app, deliberately narrow in scope: errors only. Success/confirmation messages stay silent, since they usually already come with a visible state change of their own (a screen transition, a button flipping to its done state) - a genuine failure with zero feedback is the actual problem silent toasts create, not a cosmetic one. Positioned above the floating nav bar (not at the bottom edge, not at the top - the offline banner already owns that space), using the same chrome-tier glass recipe as the nav bar and search bars. Its `max-width` is matched to `.bottom-nav`'s own at every one of the four wider breakpoints (620px → 680px → 760px → 820px), rather than staying at its own fixed 420px while the nav bar it's visually paired with kept scaling up without it - the two are meant to read as one consistent family of floating controls regardless of screen size, not one that grows and one that doesn't. Auto-dismisses after 4.5 seconds, or on tap. A new error replaces whatever's currently showing rather than queueing - errors are rare enough now (roughly 40 real failure paths across the whole app, not everything that used to pass through the old toast system) that a queue isn't needed.

## Dormant show nudge

A TV show sitting in the library, still incomplete, with no activity in 60+ days is easy to lose track of entirely once it's not fresh in Continue Watching's air-date ordering anymore. `getDormantShowToNudge()` (checked every time Home's Continue Watching renders) picks at most one such show - the single most dormant one, not every qualifying show at once - excluding anything already Stopped Watching or fully watched (`isTVUpToDate`/`isTVFinished` - nothing left to be dormant about). "Activity" (`getLastShowActivity`) is the latest `watchedAt` across its episodes, or when it was added if nothing's been watched yet at all - added-but-never-started is exactly as dormant as started-then-abandoned.

Surfaced as one small dismissible card above the normal rows (`.dormant-nudge-card`), not a toast - this isn't tied to an action that just happened, so it needs its own quiet moment rather than piggybacking on one. Two actions: "Still Watching" dismisses it for the rest of this session only (`dormantNudgeDismissedThisSession`, a plain in-memory `Set`, nothing persisted to Firestore) - a soft, low-stakes nudge doesn't need a permanent decision, so it's fine to quietly resurface on a later visit if the show is still genuinely untouched by then. "Stop Watching" calls the same `markShowStoppedById` the Continue Watching swipe gesture already uses.

## Add to Home Screen prompt

Shown once, a couple seconds after the main app becomes visible for someone not already using the installed version - `isRunningStandalone()` (checking `display-mode: standalone` / `navigator.standalone`) is the one reliable, unspoofable signal available, and permanently suppresses the prompt for anyone it's true for. Everything else is the person self-reporting: there's no cross-platform event that fires when someone actually completes the manual iOS Share → Add to Home Screen flow, so "Added" can only ever be them confirming it, not the app verifying it. Instructions are platform-aware (Share sheet wording on iOS, browser-menu wording elsewhere). "Added" sets a permanent flag (never shown again on that device); "No thanks" - or tapping outside the dialog - only suppresses it for the current session, so a genuine next visit asks again rather than being silenced by one decline.

## Offline banner

Pinned to the top via `position: sticky`, not `fixed` - the difference matters here specifically: sticky still occupies real space in normal document flow while visible, so the app's own content (Home, Library, everywhere `.page` content lives) shifts down to make room for it rather than the banner floating over the top of whatever was already there. Only affects normal-flow content this way - other full-screen overlays in the app (the auth screen, modals) are `position: fixed` themselves, which by definition can't respond to a sibling's presence regardless of technique; those still just layer via z-index if the connection happens to drop while one's open.

## iOS keyboard scroll-hijack workaround

A still-current, longstanding WebKit bug (#191204): when the on-screen keyboard opens and the page has nothing left to scroll (an empty search results list, a library with only a few items, a short country list), iOS falls back to scrolling the raw document instead of absorbing the keyboard's own gesture internally - and while that fallback is active, the text caret gets computed against a desynced layout viewport and can land somewhere other than where the text actually is. Content-length dependent, which is why it read as intermittent rather than consistently broken. All 6 search inputs in the app (Discover, both Library sub-tabs, both Upcoming sub-tabs, the region picker) give the page guaranteed extra scroll headroom only while actually focused, via a class (`body.keyboard-scroll-safety`, 60vh of bottom padding) toggled on `body` on focus/blur - not permanently, so a short page doesn't show a large empty gap under its own content the rest of the time. A separate, different caret bug (a backdrop-filter compositing quirk, always reproducible rather than content-dependent) was already fixed earlier on `.search-box` itself - both needed fixing, for different reasons.

Switching tabs (`showPage()`) while a search input was still focused could also leave that class stuck on indefinitely, as one contributing cause among others (see "Grid rows stretching to fill empty space" below for the actual main one) - the browser doesn't reliably fire an input's own `blur` event just because its container gets hidden via `display:none` a moment later (a tab switch), rather than actually removed from the DOM, so relying on `blur` alone wasn't enough. `showPage()` now blurs a focused search input directly (fires reliably, unlike waiting on the container to hide first) and removes the class unconditionally right after, as a second guarantee that holds regardless of how it got left on.

## Grid rows stretching to fill empty space

The real cause, found after the fix above turned out not to be the whole story: CSS Grid's default `align-content` (`normal`, which resolves to `stretch` for `auto`-sized tracks) stretches row tracks to fill any extra height their container happens to have, rather than sizing rows to their actual content and leaving genuine leftover space below them the way flexbox and block layout both do by default. Invisible on a grid item with no background of its own (nothing to see stretch), but the container - and so the page itself - stays exactly as tall as if it had, which shows up as a large, genuinely scrollable empty gap under otherwise completely normal-looking content. Worse the shorter the real content is relative to the space available (a short Discover search-results list is the case this was actually reported against), and present on every device, since it's a CSS behavior, not a viewport-size or platform quirk. Every grid in the app now sets `align-content: start` explicitly rather than relying on the default - `.stats`, `.wrapped-recap-grid`, `.library-grid`, `.poster-picker-grid`, `.skeleton-grid`, `.search-type-toggle`, `.segmented-toggle`, `.avatar-picker-grid`, `.modal-actions-row`, `.modal-actions.movie-actions-grid`, `.continue-group`, and `.search-results-grid`. `.bottom-nav` is the one deliberate exception - it has its own fixed `height: 70px` rather than sizing from content, so the default stretch behavior is actually what's wanted there (its single row of buttons should fill that fixed height, not sit shorter than it).
